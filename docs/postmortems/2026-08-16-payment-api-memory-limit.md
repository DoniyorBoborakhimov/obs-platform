# Postmortem: занижение лимита памяти payment-api

**Дата:** 2026-08-16
**Длительность:** 06:26 — 06:40 (14 минут)
**Severity:** SEV-3 (без влияния на пользователей, деплой заблокирован)
**Автор:** Doniyor Boborakhimov
**Статус:** закрыт

---

## Сводка

Лимит памяти контейнера `payment-api` был изменён напрямую в кластере
командой `kubectl patch`, минуя git: с 256Mi до 48Mi, затем до 40Mi и 32Mi.
При лимите 32Mi новые поды не могли запуститься — приложению требуется ~38Mi.
Поды входили в `CrashLoopBackOff` с `OOMKilled` через 2 секунды после старта.

Пользователи не пострадали: механизм rolling update не удалял работающие поды,
пока новые не станут Ready. Сервис продолжал обслуживать трафик на старой
ReplicaSet, но был **заблокирован для любых обновлений**.

Ни один из настроенных алертов инцидент не обнаружил.

## Причина (пять «почему»)

```
Почему поды падали?
  → OOMKilled: лимит 32Mi при фактическом потреблении ~38Mi

Почему лимит был занижен?
  → изменён напрямую в кластере через kubectl patch, минуя git

Почему это технически удалось?
  → нет RBAC-ограничения на изменение ресурсов в namespace banking
    и нет GitOps-контроллера, который вернул бы состояние к описанному в git

Почему инцидент не заметили сразу?
  → все алерты построены на симптомах пользователя (ошибки, латентность,
    доступность), а пользователь не пострадал

Почему пользователь не пострадал?
  → rolling update с maxUnavailable не удаляет работающие поды,
    пока новые не станут Ready — сработала штатная защита
```

**Системная причина:** отсутствует технический барьер между ручным изменением
и продом. Состояние кластера может расходиться с git без обнаружения.

**Вторичная причина:** монокультура алертов — только симптомные, без
диагностического слоя.

---

## Что сработало

Эти механизмы предотвратили отказ, их нельзя убирать:

1. **Rolling update с maxUnavailable** — старые поды не удалялись, пока новые
   не станут Ready. Именно это спасло трафик.
2. **Readiness-проба** — неготовые поды не попали в endpoints Service.
3. **`kubectl rollout status`** — команда честно показала застрявший выкат,
   не отрапортовав ложный успех.
4. **`rollout history`** — сравнение ревизий 5 и 6 сразу показало разницу
   в ресурсах, диагностика заняла минуты.
5. **Манифест в git** — позволил восстановить *правильное* состояние,
   а не просто предыдущее (которое тоже было сломанным).

---

## Что не сработало

1. **Нет алерта на OOMKilled.** Под убивался по памяти — мониторинг молчал.
2. **Нет алерта на приближение к лимиту.** Потребление 80% от лимита
   держалось несколько минут без единого сигнала.
3. **Нет алерта на застрявший выкат.** Deployment не сходился более 5 минут,
   никто не узнал.
4. **Нет защиты от расхождения кластера с git.** Ручное изменение осталось
   в кластере на неопределённый срок.
5. **CHANGE-CAUSE пустой во всех ревизиях.** История деплоев есть,
   причины изменений — нет.
6. **Обнаружение вручную.** Без плановой проверки инцидент жил бы до первой
   попытки деплоя или падения ноды.

## Извлечённые уроки

**Сайзинг по стартовому потреблению — ошибка.** Свежий под ест 32–35Mi,
через час работы — 39–40Mi. Память растёт: FastAPI лениво подгружает обработчики,
счётчики Prometheus накапливают ряды, интерпретатор держит кэши.
Лимит, подобранный по стартовому значению, приводит к падению через сутки
под нагрузкой — как правило, ночью.

Правильный подход: `max_over_time(container_memory_working_set_bytes[7d])`
плюс запас 1.5–2x.

**Алерты только на симптомы пользователя — необходимое, но недостаточное условие.**
Классический принцип SRE «алертить на то, что видит пользователь» верен,
но оставляет слепую зону: латентные сбои, при которых система уже сломана,
а последствия ещё не наступили. Нужен второй слой — диагностические алерты,
которые не будят ночью, но попадают в очередь на разбор.

**Три уровня алертинга:**

| Уровень | Кто реагирует | Пример |
|---|---|---|
| page (critical) | дежурный немедленно | сервис лежит, бюджет горит быстро |
| ticket (warning) | команда в рабочее время | OOMKilled, застрявший выкат |
| info | никто сразу, материал для трендов | короткие всплески ошибок |

**Отсутствие видимого влияния ≠ отсутствие инцидента.**
Разбирать нужно и те случаи, где повезло — именно они показывают,
насколько тонкая грань отделяла систему от отказа.

**`2>/dev/null` — опасная привычка.** В ходе работы первая попытка воспроизвести
инцидент провалилась молча: патч был отклонён API (limits < requests),
но сообщение об ошибке ушло в никуда. Подавлять stdout допустимо,
stderr — почти никогда.
